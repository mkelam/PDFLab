# PDFLab Architecture Review – Pros & Cons

## Pros
- **Production-ready HTTP stack** – `backend/src/server.ts:1-172` wires dotenv, Sentry (with PII scrubbing), helmet/cors/compression, guest-session cookies, attribution capture, centralized rate limiting, and a `/health` probe that exercises both MySQL and Redis before the API routers mount.
- **Queue-based conversion pipeline** – `backend/src/jobs/conversion.job.ts:1-210` plus `backend/src/services/cloudconvert.service.ts:1-220` show a resilient Bull worker that tracks progress, retries, guest/paid storage semantics, usage logging, and delayed cleanup while encapsulating CloudConvert-specific concerns (OCR tuning, merge/compress modes) away from controllers.
- **Granular admin authorization** – `backend/src/middleware/admin.middleware.ts:1-115` with `backend/src/routes/admin.routes.ts:1-118` defines a matrix of permissions/roles (support, finance, admin, super-admin), applies them to every admin endpoint, and funnels actions through the audit log middleware for traceability.
- **Thoughtful guest-to-user funnel** – `backend/src/services/guest-session.service.ts:1-210` and `backend/src/middleware/guest.middleware.ts:48-210` hash IPs, enforce TTLs, mint httpOnly cookies, and surface targeted upgrade CTAs so guests, attribution logic, and analytics middleware can coordinate.
- **Consistent front-end error UX** – `lib/api-error-handler.ts:1-124`, `lib/enhanced-error-handler.ts:1-122`, and their consumption inside `components/UnifiedConversionInterface.tsx:98-164` funnel backend responses through structured error types, reusable modals (`ErrorDisplay`), and analytics hooks instead of ad-hoc `alert()`s.
- **Sign-up pipeline ties growth levers together** – `backend/src/controllers/auth.controller.ts:1-230` combines password policy enforcement, promo-code handling, partner attribution (`middleware/attribution.middleware.ts:1-120`), and transactional email hooks into the registration flow instead of sprinkling those concerns across controllers.

## Cons
- **App shell forces everything into a client bundle and pings the API on every mount** – `app/ClientLayout.tsx:1-38` wraps the entire tree in a `'use client'` layout and immediately calls `performStartupHealthCheck` from `lib/api-health.ts:34-90`, so even static marketing pages drag in all client dependencies and trigger a cross-origin fetch that can hang for 5 s on slow networks.
- **Onboarding context never runs because `useAuth` does not expose `isAuthenticated`** – `contexts/OnboardingContext.tsx:95-355` destructures `{ isAuthenticated }` but `AuthProvider` only supplies `{ user, isLoading, login, logout, signup }` (`contexts/AuthContext.tsx:229`), which means `shouldShowOnboarding()` always returns false and the product tour never renders despite the backend having full onboarding APIs.
- **Session timers + token warning are dead code** – `SessionProvider` only reads from `localStorage` and exposes `refreshSession`/`endSession` (`contexts/SessionContext.tsx:26-61`), yet nothing in the repo invokes those methods (search only finds the definitions), so `TokenExpirationWarning` (`components/TokenExpirationWarning.tsx:12-49`) never receives a `tokenExpiration` timestamp and can’t alert users before logout.
- **TypeScript/Lint errors are intentionally ignored** – `next.config.mjs:3-12` disables both ESLint and TS build failures, which is why the `useAuth`/`isAuthenticated` mismatch ships unnoticed; this setting makes regressions hard to catch in CI/CD.
- **Unified conversion UI is a 1,000+ line monolith** – `components/UnifiedConversionInterface.tsx:1-1089` mixes drag/drop, quota logic, API orchestration, guest funneling, analytics, and JSX render paths in a single component, making it hard to memoize heavy computations, unit-test edge cases, or split functionality for e.g. mobile vs desktop.
- **Rate limiter order prevents paid-tier limits** – The upload route registers `uploadLimiter` before `optionalAuthMiddleware` (`backend/src/routes/conversion.routes.ts:21-34`), but `uploadLimiter` reads `req.userPlan` (`backend/src/middleware/ratelimit.middleware.ts:34-66`). Because `req.userPlan` isn’t set yet, every user—paid or not—gets the free-tier limit of 10 uploads/hour.
- **Merge endpoint isn’t actually protected** – `backend/src/routes/conversion.routes.ts:57-81` advertises “Merge PDFs requires authentication” but never wires `authMiddleware` into `router.post('/merge', …)`, so unauthenticated guests can hit `/api/merge` and consume infrastructure you expected to keep behind a paywall.
- **Guest quotas are inconsistent between UX and enforcement** – The middleware tells users “You’ve used your free guest conversion” and returns 429 after one attempt (`backend/src/middleware/guest.middleware.ts:136-158`), yet `GuestSessionService` allows `MAX_CONVERSIONS = 10` per IP/session (`backend/src/services/guest-session.service.ts:27-155`). That mismatch makes it impossible to reason about actual guest limits or A/B test funnels.
- **Quota analytics never fire** – `trackQuotaReached` only logs events when the error payload is `'Guest quota exceeded'` (`backend/src/middleware/analytics.middleware.ts:183-204`), but the middleware emits `'Daily limit reached'` (`backend/src/middleware/guest.middleware.ts:136`), so you never capture the conversion data you’re trying to analyze.
- **Some API calls skip the token-refresh path** – `pdflabAPI.convertPDFToImages` (`lib/api.ts:332-382`) and `pdflabAPI.mergePDFs` (`lib/api.ts:390-470`) use bare `fetch` with manual headers instead of `fetchWithTokenRefresh`, so expired access tokens instantly boot users, while other operations silently retry; that inconsistency makes session expiry bugs hard to diagnose.
