## Story

**As a** DevOps engineer,
**I want** to grant wildcard permissions to the pdflab_staging MySQL user,
**so that** the backend container can connect from any IP address and survive restarts.

---

## Context

Currently, the MySQL user `pdflab_staging` only has permissions from a specific IP:
```sql
'pdflab_staging'@'172.20.0.3'  ❌ OLD IP - Container moved to 172.20.0.5
```

Docker assigns new IPs on container restart, breaking database connectivity. We need wildcard permissions:
```sql
'pdflab_staging'@'%'  ✅ ANY IP - Works forever
```

---

1. ✅ New MySQL user `pdflab_staging_new` created with wildcard host (`@'%'`)

4. ✅ Permissions verified via `SHOW GRANTS`
5. ✅ Test connection from backend container succeeds

## Dev Notes

### MySQL Commands Reference

**Full Grant Statement**:
```sql
-- Connect as root
docker exec -it mysql-staging mysql -u root -p

-- Create user with wildcard
CREATE USER 'pdflab_staging_new'@'%' IDENTIFIED BY 'StagingDB2024!UserPass';

-- Grant all privileges on staging database
GRANT ALL PRIVILEGES ON pdflab_staging.* TO 'pdflab_staging_new'@'%';

-- Apply changes
FLUSH PRIVILEGES;

-- Verify
SHOW GRANTS FOR 'pdflab_staging_new'@'%';

-- Expected output:
-- GRANT USAGE ON *.* TO `pdflab_staging_new`@`%`
-- GRANT ALL PRIVILEGES ON `pdflab_staging`.* TO `pdflab_staging_new`@`%`
```

### Why Create New User?

**Option A: Modify Existing User** ❌ (Not recommended)
```sql
-- This WON'T work - can't change host
RENAME USER 'pdflab_staging'@'172.20.0.3' TO 'pdflab_staging'@'%';
-- ERROR 1396: User doesn't exist

-- This works but loses original user
DROP USER 'pdflab_staging'@'172.20.0.3';
CREATE USER 'pdflab_staging'@'%' IDENTIFIED BY 'password';
-- RISKY: If password wrong, lose access
```

**Option B: Create New User** ✅ (Recommended)
```sql
-- Old user still works (fallback)
'pdflab_staging'@'172.20.0.3' -- ✅ Untouched

-- New user works from any IP
'pdflab_staging_new'@'%' -- ✅ New wildcard user

-- If new user works, remove old user later
DROP USER 'pdflab_staging'@'172.20.0.3';
```

### Environment Variable Update

**Backend .env file**: `backend/.env` or container `/app/.env`

**Change**:
```bash
# Old (specific IP only)
DB_USER=pdflab_staging

# New (wildcard)
DB_USER=pdflab_staging_new
```

**Alternative: Keep Same Username** (if you prefer consistency)
```sql
-- Option: Create new user with SAME name but different host
CREATE USER 'pdflab_staging'@'%' IDENTIFIED BY 'StagingDB2024!UserPass';
GRANT ALL PRIVILEGES ON pdflab_staging.* TO 'pdflab_staging'@'%';
FLUSH PRIVILEGES;

-- No .env change needed! Backend will use wildcard user
```

### Docker Network Context

**Current Docker Network**: `bridge` (default) or custom network
**IP Range**: Typically `172.17.x.x` or `172.20.x.x`
**Why IPs Change**: Docker assigns IPs sequentially on container start

**Verify Network**:
```bash
# Find network
docker network ls
docker network inspect bridge

# Find container IPs
docker inspect pdflab-backend-staging | grep IPAddress
docker inspect mysql-staging | grep IPAddress
```

### Security Considerations

**Production**: NEVER use `@'%'` wildcard!
- Use specific IP ranges: `@'172.20.%'`
- Use Docker network isolation
- Use MySQL 8.0 native authentication

**Staging**: `@'%'` is acceptable because:
- Environment is isolated (no external access)
- Enables faster development iteration
- Survives container restarts

**Password Policy**:
- Min 16 characters
- Mixed case, numbers, symbols
- Rotate quarterly
- Don't reuse production passwords

### Testing Checklist

After granting permissions, verify:

1. **User exists**:
   ```sql
   SELECT user, host FROM mysql.user WHERE user LIKE 'pdflab%';
   ```

2. **Permissions correct**:
   ```sql
   SHOW GRANTS FOR 'pdflab_staging_new'@'%';
   ```

3. **Can connect from container**:
   ```bash
   docker exec -it pdflab-backend-staging sh
   mysql -h mysql-staging -u pdflab_staging_new -p pdflab_staging
   ```

4. **Can query database**:
   ```sql
   SHOW TABLES;
   SELECT COUNT(*) FROM users;
   ```

5. **Backend app can connect**:
   - Update DB_USER in .env
   - Restart backend container
   - Check logs for successful connection
